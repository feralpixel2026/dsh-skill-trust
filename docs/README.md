# 截图清单

README 顶部的截图占位目前引用两张图。下表是拍摄要求，照做即可替换占位。

## 待补截图一览

| # | 文件名 | 拍的是什么 | 建议尺寸 | README 中的引用位置 |
| --- | --- | --- | --- | --- |
| 1 | `docs/screenshot-market.png` | 市场页主界面 | 1440 × 900（或 2880 × 1800 @2x） | 第 12 行占位段落，替成 `![市场页](docs/screenshot-market.png)` |
| 2 | `docs/screenshot-detail.png` | 详情页主界面 | 1440 × 900（或 2880 × 1800 @2x） | 同上，紧接着市场页图片的下一行 |

两张都用**同一窗口宽度**拍摄，README 里并排/上下排才不跳。宽度小于 1200 px 时详情页右栏（380px 侧栏）会被挤压，失去展示价值。

## 图 1：市场页 `docs/screenshot-market.png`

**要拍到的元素**（缺一个就重拍）：

- 左侧栏的「源盾 Skills」入口处于选中态；
- 顶部搜索框；
- 排序控件（综合 / 下载量 / 收藏量 / 最近上新）；
- 筛选区三组（场景分类 / 安全状态 / 运行要求）；
- 三列卡片网格，**至少露出 6 张卡片**，让「三列」这件事看得出来；
- 卡片上可见安全状态徽标与下载量。

**拍摄建议**：

- 搜索框留空，展示默认列表；
- 选「综合」排序的默认态——这是用户第一次看到的样子；
- 卡片上的名称选真实、可读的条目，不要露出内测/占位数据；
- 有加载中骨架屏或空状态就等加载完再拍。

## 图 2：详情页 `docs/screenshot-detail.png`

**要拍到的元素**：

- 左侧五页签（能力分析 / 安全审计 / Skill.md / Skill 文件 / 历史版本），**默认停在「能力分析」或「安全审计」**——后者更能体现产品差异点；
- 右侧 380px 侧栏：流光安装框 + 安全状态 / 许可合规 / 活跃度 / 来源信息四张卡；
- 头部：图标、名称、来源标识、审计状态、版本、更新时间。

**拍摄建议**：

- 如果停「安全审计」页签，选一个**六维雷达图有真实结论**的 Skill（不是「分析中」），否则雷达图是空的；
- 若停「能力分析」，选能力画像 `capabilityStatus` 为 `SUCCEEDED` 的条目，否则字段全为 `null`，画面会是空卡片；
- 安装按钮保持默认未点击态。

## 拍摄与压缩要求

1. **窗口宽度固定**在 1400–1600 px 之间（推荐 1440），Windows 显示缩放 100%；
2. 用系统截图或浏览器 DevTools 的设备模拟整页截图，**不要拍进桌面、任务栏、其他窗口**；
3. 不留光标、不留 tooltip、不留 DevTools 面板；
4. **不要露出个人信息**：用户名路径、其他打开的项目名、通知弹窗；
5. 导出为 PNG（不要 JPEG，界面文字会糊）；
6. 单张控制在 **500 KB 以内**，超了用 `pngquant`/ImageOptim 压一遍——README 首屏加载两张 2 MB 的图体验很差；
7. 可选：同时在 `docs/` 放一份 `@2x` 版本（`screenshot-market@2x.png`），README 里用 `<img width="1440">` 引用，高分屏更清晰。**不做也可以，不是发布阻塞项。**

## 拍完怎么接进 README

当前 README 第 12 行是这样一句占位：

```
> 截图待补：`docs/screenshot-market.png`（市场页）、`docs/screenshot-detail.png`（详情页）。
```

把这一整行删掉，替换为：

```markdown
![市场页：搜索、排序、筛选与三列卡片](docs/screenshot-market.png)

![详情页：五页签、六维安全审计与右侧信息卡](docs/screenshot-detail.png)
```

注意：Markdown 图片的 `alt` 文字会被屏幕阅读器和图床预览使用，不要空着。

## 给 Lead 的建议：占位写法本身的问题

当前「截图待补」的写法有几个隐患，建议改（**本次未改 README，等你定**）：

1. **它是引用块（`>`），视觉上像正文提示而非待办标记**。发布后如果你忘了替换，读者会直接看到「截图待补」，第一印象是项目没做完。
2. **渲染成 HTML 后看不出差异**。行内代码包着的路径在 GitHub 上会显示为等宽文本，读者可能以为图已经在了，点开 README 才发现是空的。
3. **容易被误认为已知缺陷**。tracker 里这类「待补」如果不删，会持续被新访客当 issue 追问。

更稳的写法（三选一）：

- **推荐：发布前直接删掉占位行**。反正图片没就位时 README 只是少两张图，比挂着「待补」体面得多。
- 想留提醒：改用 HTML 注释，渲染不可见——
  ```markdown
  <!-- TODO 发布前补截图：docs/screenshot-market.png、docs/screenshot-detail.png，见 docs/README.md -->
  ```
- 想让 CI 拦住：在 CI 里加一步 grep 检查 `截图待补`，存在就 fail，从机制上保证不会漏。这条最可靠，但要看你觉得值不值得为它加一步 CI。

另外，如果两张图决定不拍，README 里那条「界面」小节本身已经有足够文字描述，删掉占位不影响可读性。
